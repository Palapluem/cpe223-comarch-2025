## 1. Pipeline 1 (Data Hazard)

### สิ่งที่ต้องทำในรูปภาพ (Boxing)
*   **C Code:** ตีกรอบคู่คำสั่ง `a=10, c=...` และ `b=20, d=...` และตีกรอบแดงที่ `e=a+b+c+d`
*   **Assembly Code:** ตีกรอบคู่คำสั่ง `str` / `ldr` ที่ใช้ register เดียวกันติดๆ กัน

### คำอธิบาย (สำหรับเขียนในรายงาน)
ใน Pipeline 1 จะเกิด **Data Hazard** ประเภท **Read-After-Write (RAW)** หรือ **Data Dependency** เนื่องจากในบางคำสั่งจำเป็นต้องใช้ข้อมูล (Source Operand) ที่เพิ่งถูกประมวลผลโดยคำสั่งก่อนหน้าทันที (ตัวอย่างเช่น การนำค่า `a` ไปใช้ต่อใน `c` หรือการใช้ค่า `d` ในการคำนวณ `e` ทั้งที่ข้อมูลยังไม่ผ่านขั้นตอน Write Back) ทำให้ข้อมูลยังไม่พร้อมใช้งาน หากไม่มีการจัดการ CPU จะต้องทำการหยุดรอ (**Stall**) หรือ Insert Bubble เพื่อรอให้ข้อมูลพร้อมก่อน ส่งผลให้เสีย Clock Cycle โดยเปล่าประโยชน์

เราสามารถแก้ไขเพื่อลดจำนวน Stall ได้โดยใช้วิธีทาง Hardware เรียกว่า **Operand Forwarding** (หรือ Bypassing) เพื่อส่งผลลัพธ์จากขั้นตอน Execution ของคำสั่งก่อนหน้า ข้ามกลับมายังคำสั่งปัจจุบันทันทีโดยไม่ต้องรอเขียนลง Register หรือใช้วิธีทาง Software ผ่าน **Smart Compiler** โดยทำการจัดเรียงลำดับคำสั่งใหม่ (**Instruction Reordering**) นำคำสั่งที่ไม่เกี่ยวข้องกันมาคั่นกลางเพื่อทิ้งช่วงเวลาให้ข้อมูลพร้อมใช้งาน ช่วยลดปัญหา Data Dependency ที่อยู่ติดกันได้

## 2. Pipeline 2 (Control Hazard)

### สิ่งที่ต้องทำในรูปภาพ (Boxing)
*   **C Code:** ตีกรอบ `if-else` ทั้งหมด
*   **Assembly Code:** ตีกรอบคำสั่ง `cmp` คู่กับ `ble`, `bge`, `b` (Branch instructions)

### คำอธิบาย (สำหรับเขียนในรายงาน)
ใน Pipeline 2 จะเกิด **Control Hazard** (หรือ Branch Hazard) เนื่องจากในโปรแกรมมีคำสั่งควบคุมทิศทางแบบเงื่อนไข (**Conditional Branch**) หรือคำสั่ง if-clause ซึ่งทำให้ Pipeline ไม่สามารถทราบล่วงหน้าได้ว่าจะต้อง Fetch คำสั่งใดเข้ามาประมวลผลต่อ (Next Program Counter is unknown) จนกว่าการประมวลผลในขั้นตอน Execute ของคำสั่งเปรียบเทียบจะเสร็จสิ้น หาก CPU "ทำนายผิด" ดึงคำสั่งผิดทางเข้ามา จะต้องทำการล้างข้อมูลใน Pipeline ทิ้งทั้งหมด (**Pipeline Flush**) ทำให้เกิดความสูญเสียเวลาที่เรียกว่า **Branch Penalty**

แนวทางการแก้ไขสามารถทำได้โดยใช้เทคนิค **Branch Prediction** ซึ่งมีทั้งแบบ Static (ทำนายตายตัว) และ Dynamic (ทำนายโดยดูประวัติ **History Table** ของโปรแกรม) เพื่อให้ CPU คาดเดาทิศทางได้แม่นยำขึ้น หรือใช้วิธี **Delayed Branch** โดย Compiler จะนำคำสั่งที่ปลอดภัย (Safe Instruction) และต้องทำแน่นอนไม่ว่าผลเงื่อนไขจะเป็นอย่างไร มาวางต่อท้ายคำสั่ง Branch เพื่อให้ CPU มีงานทำระหว่างรอผลการตัดสินใจ แทนที่จะปล่อยให้ Pipeline ว่าง (Stall)

## 3. Pipeline 3 (Loop / Complex Hazard)

### สิ่งที่ต้องทำในรูปภาพ (Boxing)
*   **C Code:** ตีกรอบใน Loop โดยเฉพาะ `sum = sum + x;`
*   **Assembly Code:** ตีกรอบ Loop Label (`.L4`), คำสั่ง `ldr/add` ในลูป และคำสั่ง `cmp/ble` ท้ายลูป

### คำอธิบาย (สำหรับเขียนในรายงาน)
ใน Pipeline 3 จะเกิดปัญหาร่วมกันระหว่าง **Data Hazard** และ **Control Hazard** ภายในโครงสร้าง Loop โดย **Data Hazard** เกิดจาก Data Dependency ของตัวแปร `sum` ที่ทำหน้าที่เป็น Accumulator ซึ่งมีการเขียนและอ่านค่าซ้ำๆ ในทุกรอบการวนลูป (`sum = sum + x`) ข้อมูลจากรอบก่อนหน้าอาจยังบันทึกไม่เสร็จเมื่อรอบใหม่ต้องการใช้ ทำให้เกิดโอกาส Stall ถี่ขึ้น ส่วน **Control Hazard** เกิดจากการตรวจสอบเงื่อนไข Loop (`j < 10`) ในทุกรอบ ซึ่งถือเป็น Conditional Branch หากทำนายผิดก็จะต้องทำการ Flush Pipeline เช่นกัน

แนวทางการแก้ไขปัญหาใน Loop คือการใช้ **Branch Prediction** ที่แม่นยำ (โดยธรรมชาติ Loop มักจะทำนายว่า Taken/วนลูปต่อ ได้ถูกต้องสูง) เพื่อลด Control Hazard และใช้วิธี **Loop Unrolling** (คลี่ลูป) เพื่อลดจำนวนครั้งที่ต้องตรวจสอบเงื่อนไขและกระโดด นอกจากนี้ การคลี่ลูปยังช่วยเปิดโอกาสให้ Compiler สามารถจัดเรียงคำสั่ง (**Instruction Scheduling**) ได้ดียิ่งขึ้น เพื่อลดผลกระทบจาก Data Hazard ภายใน Loop ได้อีกทางหนึ่ง
